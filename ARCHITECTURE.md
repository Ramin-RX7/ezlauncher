# ezlauncher — architecture reference

A map of the codebase for AI agents (and people) doing a task here. Read this **before** grepping: it gives the flow, the file layout, the invariants, and "where to add X" recipes, so you rarely need to open more than the two or three files a change actually touches.

- What to build and why lives in [scopes.md](scopes.md). All eight scopes (00–07) are **implemented**.
- The rules you must follow (security, IPC, styling, files-on-disk, cross-platform) live in [CLAUDE.md](CLAUDE.md). This document does not repeat them; it shows where things are.
- Tests sit next to their file (`foo.ts` → `foo.test.ts`) and are omitted from the file tables below. When you change a file, update or add its test.

## 1. The three processes and the boundary between them

```
┌── src/main ─────────────┐   IPC (typed contract)   ┌── src/renderer ────────────┐
│ Electron main process   │ <───────────────────────>│ React UI (no Node/fs)      │
│ all fs, network, spawn  │   src/shared/ipc.ts       │ TanStack Query + store     │
└─────────────────────────┘         ▲                 └────────────────────────────┘
                                     │ contextBridge
                          ┌── src/preload ──┐
                          │ window.api only │
                          └─────────────────┘
```

- **`src/main/`** does every side effect (files, network, child processes). Split into pure core (`minecraft/`, `core/`, `auth/`, `profiles/`, `modsources/`, `validation/`, `settings/` — **no Electron imports**, unit-testable) and the Electron glue (`services/`, `ipc/`, `window.ts`, `index.ts`, `log.ts`).
- **`src/preload/`** exposes exactly one object, `window.api`, with `invoke`, `on`, and `pathForFile`. Nothing else crosses.
- **`src/renderer/`** is React only. It never imports Node, Electron, or `src/main`. ESLint enforces this.
- **`src/shared/`** holds the types both sides use: the IPC contract (`ipc.ts`), the data shapes (`launcher.ts`), and the argument splitter (`args.ts`). No Node or DOM types here.

### Boot flow (`src/main/index.ts`)

0. **Update flags first** (`updates/startupFlags.ts:readUpdateFlags`): `--ezl-update-finish=<target>` means this process is an update's new version finishing the swap (`updates/apply.ts:finishUpdate`, no window, no lock, then exit); `--ezl-updated=<pid>` waits for the old version to exit before taking the lock. `EZL_USER_DATA` (test hook) points `userData` elsewhere.
1. Single-instance lock; a second launch focuses the running window. A profile's desktop shortcut starts the launcher with `--ezl-profile=<id>` (`startup.ts:profileFromArgv`, found anywhere in argv, `safeId`-checked): the first start opens the window at `#/profiles/<id>`, a second one sends `app:openProfile` and `AppShell` navigates there.
2. `app.whenReady()` → `initFromBootstrap()` reads `bootstrap.json` (in Electron `userData`); if it names a data folder, `startService(dir)` builds the `LauncherService` for it. Then `startUpdates()` (`services/updates.ts`) creates the app's one update service (also without a data folder) and cleans what a finished update left.
3. `registerIpc()` wires every `register…Ipc()` handler.
4. `createMainWindow()` (sandboxed) loads the renderer.
5. Renderer `App.tsx` → `Root()` queries `setup:getState`; with no data folder it shows `SetupPage`, otherwise the `HashRouter` app. Hash routing because the packaged app loads from `file://`.

### The IPC contract (the pattern to copy for any new call)

- **One source of truth:** `src/shared/ipc.ts` declares `IpcInvokeContract` (request/response) and `IpcEventContract` (main→renderer push), plus the runtime allow-lists `INVOKE_CHANNELS` / `EVENT_CHANNELS`. Preload only forwards channels in those lists.
- **Main registers** with `handle(channel, fn)` from `ipc/register.ts`. Thrown `AppError(code, msg)` is caught and returned as `{ ok: false, error: { code, message } }` — errors never cross IPC as exceptions.
- **Main pushes** with `broadcast(channel, payload)` to all windows.
- **Renderer calls** `invoke(channel, ...args)` from `lib/api.ts`, which unwraps `{ ok }` and throws `IpcCallError` (carrying `code`) on failure. `lib/errors.ts` maps a `code` to a localized `errors.*` string (add new codes to its `KNOWN` list **and** to `en.json`).
- **Renderer subscribes** with `useIpcEvent(channel, handler)` or, for store wiring, in `state/LauncherEvents.tsx`.
- Handlers delegate to `getService()` (the per-data-folder `LauncherService`). File dialogs run main-side (in `ipc/mods.ts`, `ipc/resourcePacks.ts`, `ipc/setup.ts`) so paths never originate in the renderer.

## 2. On-disk data directory layout

Everything is built through `src/main/minecraft/paths.ts` (`createPaths(dataDir)` → `Paths`). The renderer never builds paths; ids are sanitized (`safeId`, `safeFolderName`, `safeJoin`) so renderer input can't escape the folder. The data folder is user-chosen (never hard-coded).

```
<dataDir>/
  versions/<id>/            <id>.json, <id>.jar, natives/, install.json (marker; written last)
  libraries/<maven path>    shared Mojang/loader libraries
  assets/                   indexes/, objects/<2>/<hash>, virtual/, log_configs/
  runtimes/<component>/      downloaded Java, manifest.json, .installed.json
  mods-store/<sha1>.jar      the shared mod library (one copy per unique jar)
  mods-store/icons/<sha1>.png
  resourcepacks-store/<sha1>.zip   the shared resource pack library (+ icons/<sha1>.png)
  shaderpacks-store/<sha1>.zip     the shared shader pack library (+ icons/<sha1>.png, the project's icon from Modrinth)
  datapacks-store/<sha1>.zip       the shared data pack library (+ icons/<sha1>.png); hard-linked into worlds/<id>/datapacks/
  profiles/<profileId>/      a profile's game folder: mods/, resourcepacks/ and shaderpacks/ (hard links into the stores; shaderpacks/<pack>.txt = Iris's options for that pack), saves/, config/ (iris.properties + .ezl-bak), options.txt (+ options.txt.ezl-bak), logs/
  profiles/.import-<id>/      a mod pack being imported (renamed to profiles/<id>/ when done); profiles/.update-<id>-<token>/ = a pack update's new files until applied (both removed at startup if left)
  worlds/<worldId>/          every world, whichever profile owns it (ezlauncher-world.json owner flag inside; datapacks/ = its data packs, hard links into datapacks-store/)
  backups/<key>/             world backups: <id>.zip each + index.json (key = world id, or <profileId>~<folder> for an unlinked world)
  modpack-backups/<profileId>/<time>.zip   the files a mod pack update replaced or removed, zipped before it ran
  launcher/                  profiles.json, accounts.json, settings.json, mods.json, resourcepacks.json, shaderpacks.json, datapacks.json, running.json, loaders/<id>.json (cache), version_manifest cache; modpacks/<profileId>.json (what a mod pack put into a profile), playtime.json (play time per profile: total + newest 200 sessions), profile-icons/<id>.png (a pack profile's icon), modpack-downloads/ (packs fetched from a site until imported; cleared at startup)
  games/<versionId>/         legacy Scope 01–02 folders, only read to migrate into profiles
```

- **Worlds** live once in `worlds/` and are **directory-linked** into each profile's `saves/` (junctions on Windows, symlinks elsewhere). `links.ts` is the only place that knows link types.
- **Mods** live once in `mods-store/<sha1>.jar` and are **hard-linked** into each profile's `mods/` (a copy where hard links fail, e.g. across drives). **Resource packs** and **shader packs** work the same way (`resourcepacks-store/` → `resourcepacks/`, `shaderpacks-store/` → `shaderpacks/`); all three use `profiles/linkedStore.ts`. Unzipped (folder) packs stay in their profile.
- **Active resource packs and their order live only in the profile's `options.txt`** (`resourcePacks`, lowest priority first). The launcher changes only those two lines, never while a game of the profile runs or starts.
- **The active shader lives only in the profile's `config/iris.properties`** (`shaderPack`, `enableShaders`), Iris's own file. The launcher changes only those two keys, never while a game of the profile runs or starts (Iris rewrites the file on start).
- **Data packs belong to worlds, not profiles.** The data pack library is keyed by **world id** (`worlds/<id>/datapacks/`). The game turns a new file there on by itself when the world loads and drops entries whose file is gone, so the launcher only links and unlinks files; a world's `level.dat` is **only read** (which packs were turned off in game, its experimental features), never written. Nothing changes while the world's owner profile runs or starts (the game keeps a world's packs open).
- **Running games** are saved in `launcher/running.json` (pid, profile, start time), so a restarted launcher still treats their profiles as playing.
- **A mod pack is a profile.** Importing a `.mrpack` makes an ordinary profile (`Profile.modpack` names the pack and version; the same pack can be imported many times). Its mods, resource packs and shaders go into the shared libraries by the usual sync adoption; its other files are plain files in the profile. `launcher/modpacks/<id>.json` lists every file the pack wrote with its SHA1, so an update replaces or removes only files still as the pack wrote them, never the user's own files or worlds.
- **`servers.dat` (a profile's Multiplayer list) is edited losslessly** (`profiles/nbtTree.ts` + `serverList.ts`): only `name`, `ip`, `acceptTextures` and the order of visible entries change; icons, hidden entries and unknown tags stay; the first save keeps `servers.dat.ezl-bak`; never while a game of the profile runs or starts.
- **App updates belong to the app, not the data folder**: `updates.json` (last check time, daily check on/off) sits in Electron `userData` next to `bootstrap.json`. The update feed is `releases.json` at the repo root, written only by `.github/workflows/feed.yml` when a release is published.
- **Markers** (`install.json`, loader marker) are written **last**, so a half-finished install reads as "not installed".

## 3. End-to-end flows (what calls what)

**Install / repair a version** — `installer.ts:installVersion` (via `InstallQueue`, one job at a time): resolve the `inheritsFrom` version-JSON chain (`versionJson.ts`, downloading missing) → fetch asset index → gather library/native/client/asset `FileTask`s (`libraries.ts`, `assets.ts`, rule-filtered by `rules.ts`) → `checkFiles` keeps only missing/bad → `downloader.ts` downloads (concurrent, `.part`, SHA1, retry) → `ensureJava` (`java.ts`) → extract natives (`natives.ts`) → `writeInstallMarker`. Loader installs go through `loaders/installLoader.ts` instead (ensures vanilla, writes the merged loader version JSON with hashes backfilled, then installs its files).

**Launch a game** — `launcherService.launch({profileId, accountId, problems})`:

1. Resolve the account → `AuthProvider.getLaunchIdentity` (offline: MD5 `OfflinePlayer:` UUID, placeholder token).
2. **Refuse** if that account already plays this profile (`ACCOUNT_PLAYING`); several games of one profile are allowed but each needs a different account.
3. `ensureProfileInstall` installs/reuses the version (a profile's pinned loader build, `Profile.loader.version`, must match exactly; otherwise any installed build of that loader is reused, or the newest stable is installed); sync worlds+mods (skipped if the profile is already running).
4. `validateMods` (Scope 05). With errors and `problems:"check"` → return `{status:"blocked", report}` (the UI shows `LaunchProblemsDialog`); `"ignore"` plays anyway; `{disable:[…]}` disables those mods first.
5. **Quick Play** (`LaunchRequest.quickPlay`: a world of the profile, or a server address): `launch` checks it first (`checkQuickPlay`: the world exists and no game of the profile runs, `WORLD_IN_USE`; the address through `shared/serverAddress.ts:parseServerAddress`), then `buildLaunchCommand` turns on the version JSON's `is_quick_play_singleplayer` / `is_quick_play_multiplayer` features with `quickPlaySingleplayer` (the world's folder in `saves/` = its id) / `quickPlayMultiplayer`. Versions without those rules (before 23w14a/1.20) join servers with `--server <host> --port <port>`; worlds there throw `QUICKPLAY_UNSUPPORTED`. `profiles:playTargets` says up front whether worlds can be started into (the version JSON, else its release date) and reads the game's server list (`nbt.ts:readServerList`, `servers.dat`, never written). Checked on 26.3: the world opens directly; a server goes straight to its connect screen.
6. `buildLaunchCommand` (`arguments.ts`) assembles argv: `[...jvm, ...extraJvmArgs, mainClass, ...game, ...extraGameArgs]`, memory/args from `resolveLaunchSettings(profile, settings)`. `launchGame` (`gameProcess.ts`) spawns detached; stdout is parsed (`gameLog.ts`) and pushed as `game:log` events keyed by `launchId`; each game writes `logs/ezlauncher-output-<account>.log`.

**Add / enable mods (local)** — jars enter via `mods:addFiles`/`addFromPicker` (picker in `ipc/mods.ts`) or are dropped into `mods/` and adopted on `sync`. `mods.ts:createModLibrary` stores by SHA1, reads metadata (`modInfo.ts`), hard-links into the profile, and enforces one version per `modId`. Each entry records `addedAs` (`user` for picked/dropped/searched mods, `dependency` for what a download pulled in; only ever promoted to `user`); older entries are inferred by `libraryDeps.ts`. The Mod library page nests dependency-only mods under the mods that need them (`components/mods/libraryTree.ts`). Compatibility is `compat.ts:checkCompat` (jar metadata first).

**Download mods (Modrinth)** — `mods:findRemote` → `modrinth.ts:findExact` → `getCompatibleVersion` → `resolveDependencies.ts:resolveInstall` builds a plan (download/reuse/missing/incompatible/replaces) → a `RemoteMatchCard` with a `planId` (kept in memory, 15-min TTL). `mods:installRemote` → `downloadMods.ts:downloadPlan` downloads into the store (SHA1-checked), records source refs, enables everything; a failed/cancelled batch removes only what it added. Hand-added jars are identified by hash in the background (`identifyFiles`, weekly recheck) to earn a Modrinth badge. **Bulk re-fetch** (`bulkFetch.ts:resolveBulk` + `downloadMods.ts:storeVersions`): `downloadLibraryMods` grabs the compatible version of every sourced library mod for a chosen version+loader; `applyProfileMods` does the same for one profile after its version changes, enabling the matches and disabling (but keeping) mods with no compatible version. Progress streams on `mods:bulkProgress`.

**Duplicate a profile / profile icons** — `duplicateProfile(id, { copyWorlds })` copies a profile's settings + enabled-mods set into a new id (worlds are owned by the `ezlauncher-world.json` flag, so the copy claims none of the originals). With `copyWorlds` (a checkbox in `DuplicateProfileDialog`, off by default), `worlds.ts:copyProfileWorlds` copies each world into the new profile's `saves/` without its flag or `session.lock`, and the next sync adopts the copies as the new profile's own; a failed copy removes the new profile again. A profile's `iconId` names a bundled renderer asset (`assets/profile-icons/*.svg`); nothing is written to disk for it.

**Validate mods (Scope 05)** — `collect.ts:collectInput` gathers enabled mods + loader build + Java + integrity file list; `integrity.ts:checkIntegrity` does a quick zip check every launch (full SHA1 only when a file changed); `validate.ts:validate` (pure) returns `issues` + `requiredBy`. Version ranges: `versions/{semver,fabricRange,mavenRange,mcVersion}.ts`. `disableCascade`/`orphanedDependencies` drive "disable problem mods" and the untick cascade. The renderer words issue codes via `issueText.ts`.

**World backups** — `profiles/backups.ts` (no Electron): `createBackup` streams a world into a zip (fflate `ZipDeflate`, `.part` then rename; `session.lock` and the owner flag left out) unless its fingerprint (names + sizes + mtimes, no file reads) equals the newest backup's; `restoreBackup` unpacks into a temp folder (every entry through `safeJoin`) and moves it into `worlds/` as a new world owned by the profile, then a sync links it; `pruneBackups` keeps at most N and none older than D days, never the newest; `backupDue` decides automatic backups. The service runs one backup job at a time (`backup:progress` / `backup:state` events → the navbar `BackupIndicator`); automatic ones run before the start (inside `launch`, Skip continues) or after the last game of a profile closes (after its sync), per settings. Manual backups are refused while the profile plays. Retention is applied after each backup, at start, and when its settings change.

**Resource packs (Scope 08)** — `profiles/packs/library.ts:createPackLibrary` is the store (adds only zips with a root `pack.mcmeta`, read through `core/zipEntries.ts` without reading the whole zip; a zip edited in place through a link is stored again under its new SHA1). `packs/profilePacks.ts` is one profile's view: `view` reads the order from `options.txt` (`gameOptions.ts`), lists library + folder packs with their compatibility (`packMeta.ts:packCompat` against the version's format from its client jar, `packFormat.ts:readGameFormat`); `setActive` links/unlinks library packs and writes both pack lines (incompatible packs also go into `incompatibleResourcePacks`, unknown ones never), backing the file up once; `followSync` fixes entries after hand renames (from `linkedStore` `reconcile`'s diff); `copyActive` (duplicate) and `translate` (version change across 1.13) keep the lists right. Sync runs inside the service's `sync()` after mod sync. Modrinth: `modrinth.ts:search` (paged, `project_type:resourcepack`) → `modsources/downloadPack.ts:downloadPack` (version for the game version, else the newest; primary `.zip`; required projects reported as `needs`) → `activatePacks` turns it on at the top. Hand-added packs are identified by hash like mods.

**Shader packs** — shaders run through the Iris mod (Fabric/Quilt; it needs Sodium). The same `createPackLibrary`, given `shaderPackKind` (`packs/shaderMeta.ts:readShaderZip`: any `shaders/` folder in the zip, as Iris checks; no metadata or icon). `packs/profileShaders.ts` is one profile's view: the active shader from `iris.properties` (`profiles/irisConfig.ts` reads/writes it the way Java's `Properties` does: latin1, `\uXXXX`, `=`/`:`/`#`/`!` escaped), its linked + folder shaders (all listed by Iris in game), the library's others, and whether it has Iris (`launcherService.hasMod`: mod id, provides or nested jar). `setActive` links a library shader and writes `shaderPack=<file>` + `enableShaders=true` (off = `enableShaders=false`, name kept, as Iris's own toggle does), backing the file up once; `remove` takes a shader out (turning it off if active; its options file stays); `followSync` renames `<pack>.txt` with the zip and follows the active entry; `copyTo` (duplicate) copies shaders, their options files and the active one. What Iris 1.11 on 26.3 does (checked): honours a name set before launch (spaces, non-ASCII, `=`, `#` escaped), rewrites the whole file sorted at start, falls back to no shaders (keeping the name) when the file is missing, writes `shaderPack=` when none, doesn't lock shader zips, and loads a zip whose `shaders/` is one folder down (a folder pack must have `shaders/` directly). Modrinth: `search` with `project_type:shader` (every shader; hits carry their loaders from the categories) → `downloadPack` with `SHADER_DOWNLOAD` (Iris version for the game version, then any loader, then Iris for any version, then newest) → the project's icon is saved → made the profile's shader. Without Iris the Shaders tab offers `AddModDialog` for `iris` (the resolver brings Sodium).

**Data packs** — the same `createPackLibrary`, given `dataPackKind` (`packMeta.ts:readDataPackZip`: a pack with a `data/` folder; an `assets/`-only zip is a resource pack). Its keys are world ids: `launcherService.syncDataPacks` passes every world in `worlds/` (a world that's gone drops its links), reconciles only the worlds of the synced profiles, and treats a world as running when its owner (`readWorldOwner`) is. `packs/worldDataPacks.ts` is one world's view: linked + folder packs with compatibility against the owner profile's **data** format (`packFormat.ts` `GameFormat.data`: `pack_version.data` / `data_major`+`data_minor`, table for 1.13), "turned off in game" and missing experimental features from `nbt.ts:readDataPackState` (`Data.DataPacks.Enabled/Disabled`, `Data.enabled_features`; read only), the library's others, and non-packs. World copies (duplicate with worlds, backup restore) are adopted by the next sync under the same SHA1; deleting a profile's worlds forgets their links. What Minecraft 26.3 does (checked): "Found new data pack file/X, loading it automatically", "Missing data pack file/X" (dropped from `Enabled`), and a pack in use is locked while the world is open. Modrinth: `search` with `project_type:datapack` (projects with data pack versions; hits still say `mod`) → `downloadPack` with `DATAPACK_DOWNLOAD` (loader `datapack` only, so never a mod jar) → added to the world. "Add to worlds…" (`dataPacks:worlds` / `addToWorlds`) puts one pack in several worlds, reporting the ones that can't change now.

**Mod packs (Modrinth `.mrpack`)** — the core is `src/main/modpacks/` (no Electron); `services/modpacks.ts:createModpackService` wires it to profiles, libraries and the site. **Read**: `readMrpack.ts:readMrpack` reads only the zip index + `modrinth.index.json` (`mrpackIndex.ts:parseIndex`: zod; every path through `safeJoin` and refused if absolute or `..`; downloads only over https from `cdn.modrinth.com`, `github.com`, `raw.githubusercontent.com`, `gitlab.com`; `env.client` `unsupported` dropped, `optional` offered; `dependencies` → Minecraft version + `fabric-loader`/`quilt-loader`/`forge`/`neoforge` and its build). A read pack waits under a token (1 h). **Import** (`importPack.ts:importPackFiles` into `profiles/.import-<id>/`): `installFiles.ts:installPackFiles` downloads each file SHA1-checked (a file a library already stores is hard-linked from its store instead), then `extractOverrides` unpacks `overrides/` with `client-overrides/` winning (one streaming pass through `core/unzip.ts`, size/count caps); the folder is renamed to `profiles/<id>/`, the manifest written, the profile added with the pack's version and **pinned loader build**, the site's project icon saved, and `sync([id])` adopts mods/packs/shaders/worlds into the libraries. Any failure removes everything. Forge/NeoForge packs are refused (`MODPACK_LOADER_UNSUPPORTED`). **Update** (`updatePack.ts`): `planUpdate` unpacks the new overrides into a staging folder (so their SHA1s are known) and compares target ↔ manifest ↔ disk per path: `add`, `update` (disk still as written), `changed` (the user changed it: kept unless ticked), `remove` (gone and unchanged), `keepRemoved`; worlds (`saves/`) are never part of it; optional files skipped at import stay skipped. `applyUpdate` zips what it will replace/remove to `modpack-backups/`, writes files by temp + rename (a hard link into a store is replaced, never written into), then the profile's version/loader/pack record and the manifest follow; the profile can't start meanwhile (`packUpdating` in `isBusy`). **Export** (`exportPack.ts`): top-level entries offered (worlds hidden; logs/caches/personal files unticked), library files a site knows (`identifyFiles` by SHA1) become index downloads with a locally computed sha512, everything else goes into `overrides/` (`core/zipWrite.ts`); the loader build is the pinned one, else the installed one, else the newest. Duplicating a pack profile copies its manifest, icon and the pack's non-library files. Modrinth: `search` with `project_type:modpack` (every loader; hits carry loaders + Minecraft versions; the UI disables Forge-only ones), `listVersions` for the version choice and updates.

**Play time** — `profiles/playTime.ts` (`launcher/playtime.json`): `gameExited` records each game's `startedAt → now` (every game of a profile counts, also restored ones). `running.json` notes `seenAt` every minute while games run; at startup `restore()` returns games that ended while the launcher was closed, recorded until `seenAt` with `approx`. `listProfiles` adds `playTimeMs`; `profiles:playHistory` gives the sessions with account names. Deleting a profile forgets it.

**Storage page** — `storage/diskUsage.ts:measureDisk` walks the data folder once (stores first; each `dev:ino` counted once, links/junctions never followed) into `STORAGE_CATEGORIES`. `storage/gameFiles.ts`: `neededGameFiles` (libraries via `collectLibraries`, asset indexes/objects, virtual dirs, log configs of every folder with an install marker; any unreadable one → `unknown`, and then neither game files nor Java are cleaned) and `orphanGameFiles` (also version folders without a marker). `services/storage.ts:createStorageService` plans six clean-ups (`libraryItems` through the libraries' `removeUnused`; `versions` no profile plays and nothing played builds on; `java` no installed version names; `gameFiles`; `backups` = orphan world backups + `modpack-backups/` + the patch-notes cache; `logs` = old logs and crash reports of idle profiles), and `clean(ids)` plans each again right before running it, in that order. Game files wait for installs, backups and data moves (`STORAGE_BUSY`). Checked read-only on a real 915 MB data folder: 0.14 s.

**Server list** — `servers:list` / `servers:save` (the whole list; `key` = an existing entry's index) → `serverList.ts:writeServers` (lossless, see §2), written atomically. Real game-written files round-trip byte for byte.

**App updates** — the feed: publishing a GitHub release runs `.github/workflows/feed.yml` → `scripts/feed.mts` (`scripts/lib/feed.mts:addRelease`: files matched by name suffix to `winSetup`/`winPortableExe`/`winPortableZip`/`linuxAppImage`, SHA-256 from the release's `SHA256SUMS.txt`, notes from CHANGELOG) → a bot commit of `releases.json` to master. The app: `updates/service.ts:createUpdateService` (app-level; wired in `services/updates.ts`) reads `FEED_URL` (raw `releases.json`) once a day (10 s after start, then hourly ticks that fetch only after 24 h; off via `updates.json`) or on Settings → Check for updates; `feed.ts:pickUpdate` picks the newest **stable** release newer than `app.getVersion()` (`shared/semver.ts`) with this build's file (`buildKind.ts:detectBuild`: `PORTABLE_EXECUTABLE_FILE` → portable exe, `Uninstall EZLauncher.exe` next to the exe → installer, other packaged Windows → zip, `APPIMAGE` → AppImage; downloads only from the repo's `releases/download/`), else the update is `blocked` (dev / unsupported / notWritable / noFile → the release page). The user downloads it (`download.ts:downloadVerified`: size + SHA-256 from the feed, `.part` then rename; the zip is unpacked to `<folder>.new` by `apply.ts:prepareUpdate`), then **Restart now** or it goes in on quit (`before-quit`). Installing is refused while `launcherService.isAnyBusy()` (installs, downloads, imports, backups, pack updates, a data move; running games don't count). `apply.ts:installUpdate`: the **portable exe** and the **zip** start the new version as a helper with `--ezl-update-finish` (+ `--ezl-update-from=<exe>.update` for the exe) and quit; the helper waits for the old pid, renames the old exe/folder to `.old` (retrying while Windows still holds it: the portable exe's stub keeps its own file open, so it can't be swapped while running), copies itself into place under the same name, starts it with `--ezl-updated=<helper pid>`; any failure puts `.old` back and starts it with `--ezl-update-failed` (banner: the update couldn't be finished). The new version deletes `.old`/`.new`/`.update` on start (`cleanupAfterUpdate`, retried). The **installer** runs the setup silently (`/S --updated [--force-run]`); the **AppImage** is renamed over the old one. Electron's `fs` treats `app.asar` as a folder, so all of this runs with `process.noAsar` on (`asPlainFiles`). Checked end to end on Windows (scratch folder, local feed via `EZL_UPDATE_FEED` + `EZL_UPDATE_TEST=install`): zip 0.2.0 → 0.2.1 in about 15 s, portable exe (renamed by the user) → 0.2.1 in about 25 s, both under the same path.

**Running games** — `minecraft/runningGames.ts`: `launch` saves every started game (pid, profile, start time) and `gameExited` removes it; at startup `restore()` brings back games whose process is alive and started after the last boot, and `watchRestored` polls them until they exit (then the normal exit handling: sync + backup). `assertNotRunning` also refuses while a game of the profile is still starting.

**World sync** — `worlds.ts:syncWorlds`: adopt saves created in-game into `worlds/`, drop worlds deleted in-game, relink each profile's `saves/` from owner flags, report orphans. Runs after the **last** game of a profile exits. `removeTree` never follows links, so deleting a profile can't touch a linked world.

**Move the data folder** — `moveData.ts:moveDataDir`: same drive = `rename`; other drive = copy the tree preserving hard links (so `mods-store` stays shared), re-point world links into the new folder, delete the old one; cancellable, progress via `setup:moveProgress`, then relaunch. Orchestrated in `ipc/setup.ts`; refused while games run or installs are busy.

**Accounts** — `auth/accounts.ts:createAccounts`: add/rename/remove, names unique ignoring case, UUID fixed at creation and kept across rename. Selection lives in `settings.selectedAccountId`.

## 6. Conventions & invariants (don't break these)

- **Add a feature the existing way.** Core modules take their deps as arguments (`paths`, `downloader`, `platform`, `fetch`, `logger`) so they stay Electron-free and testable — never import `electron` under `minecraft/`, `core/`, `auth/`, `profiles/`, `modsources/`, `modpacks/`, `validation/`, `settings/`.
- **All UI text** goes through i18n keys in `en.json` (`t('…')` is type-checked). No hard-coded user-facing strings.
- **Styling** uses theme tokens only (`bg-surface`, `text-muted`, `rounded-ezl`, …) and logical properties (`ms-`, `pe-`, `start-`, `border-e`) for RTL. No raw colors.
- **JSON on disk**: write with `writeJsonAtomic`, read with `readJson(path, schema)`. Validate every JSON from disk or network with Zod. Build every path through `paths.ts`.
- **Never bundle/re-host Mojang files**; always download and verify by SHA1; skip already-valid files; obey library `rules`; treat version ids as opaque, sort by `releaseTime`.
- **Offline identity**: UUID = `nameUUIDFromBytes("OfflinePlayer:" + name)` (MD5 v3), generated once and stored; renaming keeps it.
- **Concurrency**: `LauncherService` runs folder work through `serialFs`; the mod library and profile/account stores each serialize their own writes. Installs go through `InstallQueue`. Don't add parallel writers to the same JSON.
- **While a profile's game runs**, block editing it, changing its mods/worlds, deleting it, and repairing/deleting its version (`assertNotRunning`, `assertVersionNotPlayed`). Sync only after the last game exits.
- **App updates never leave the user without a working launcher**: everything that can fail (download, checksum, unzip) happens before the old version is touched; a swap that fails puts `.old` back and starts it. The replaced exe/folder keeps its path, so shortcuts keep working. Updates come only from the repo's releases, checked against the SHA-256 in `releases.json`. Pre-releases are never offered.
- **Mod pack updates only touch the pack's files**: a file is replaced or removed only while its SHA1 still matches the manifest (or the user ticked it); worlds and the user's own mods never; replaced files are zipped first. Files are replaced by temp + rename, never written in place (they may be hard links into a store).

## 7. "Where do I add…?" recipes

- **A new IPC call** → declare it in `shared/ipc.ts` (contract + `INVOKE_CHANNELS`/`EVENT_CHANNELS`), add a `handle()` in the right `ipc/*.ts`, add a method on `launcherService.ts`, call it from the renderer via `invoke()`. New error codes → `lib/errors.ts` `KNOWN` + `en.json` `errors.*`.
- **A new page/route** → add the page in `pages/`, a `<Route>` in `App.tsx`, and a nav link in `components/AppShell.tsx`.
- **A new mod source** (e.g. CurseForge) → implement the `ModSource` interface in `modsources/<site>.ts`, register it in `modsources/registry.ts`. `resolveDependencies.ts`, `downloadMods.ts`, and the whole UI already work through the interface.
- **A new mod loader** (Forge/NeoForge) → implement `LoaderProvider` in `minecraft/loaders/<loader>.ts`, register in `loaders/registry.ts`; extend `acceptedLoaders` in `profiles/compat.ts` if it loads others' mods.
- **A new setting** → add the field to `LauncherSettings` (`shared/launcher.ts`), the file+patch schema and `DEFAULT_SETTINGS` (`settings/settings.ts`), and UI in `pages/SettingsPage.tsx`. A per-profile override also goes through `resolveLaunchSettings` and the profile schema.
- **A new validation check** → add it in `validation/validate.ts` (pure), a `ValidationProblem` variant in `shared/launcher.ts`, wording in `components/mods/issueText.ts` + `en.json`.
- **A new pack kind** → a `PackKind` for `createPackLibrary` (store/icon/JSON paths in `paths.ts`, a zip reader, error codes), its own activation module (resource packs: `options.txt` via `profilePacks.ts`; shaders: `iris.properties` via `profileShaders.ts`; data packs: none, the game turns files on, via `worldDataPacks.ts` keyed by world), a `syncPackKind` + `identifyPendingPacks` call in the service, a `PackDownloadKind` for `downloadPack`, and a `kind` for `PackLibraryTab`/`AddPacks`/`PackIcon`. The Modrinth adapter takes a `projectType`; `RemoteSearchDialog` gives the search UI.
- **A new i18n string** → add it under the right top-level key in `en.json` (`app, nav, setup, versions, loaders, play, log, settings, errors, profiles, worlds, servers, shortcut, time, playTime, storage, updates, accounts, versionsPage, mods, remote, validation, launchProblems, library, resourcePacks, shaders, dataPacks, modpacks`).

## 8. Tooling & tests

- Commands (see CLAUDE.md): `npm run dev`, `npm run build`, `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm test`. Node-only launcher CLI: `npm run mc -- <list|install|check|command|launch> [id] --data <dir>`.
- **Before finishing any change:** `npm run typecheck && npm run lint && npm run format:check && npm test`.
- **Tests** (Vitest): Node environment for `src/main` + `src/shared`, jsdom for `src/renderer` (`src/renderer/src/test/setup.ts` adds jest-dom + a `ResizeObserver` stub). Core modules test with fakes — `minecraft/testing/{fakeFetch,fakeMojang}.ts`, `modsources/testing/fakeModSource.ts`, `profiles/testing/*` — and never touch the network or a real data folder. Renderer tests use `src/renderer/src/test/{mockApi,fixtures}.ts`.
